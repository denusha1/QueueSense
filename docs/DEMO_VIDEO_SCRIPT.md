# QueueSense Enterprise demo script

**Target length · 4 minutes 15 seconds**

Use a local synthetic environment with JWT enabled. Prepare two browser windows, the clinic staff workspace and an anonymous patient tracker. Open the architecture diagram, partner OpenAPI file, staging results and performance table in separate tabs. Crop the tracker address bar and keep cookies, QR codes, signing keys and tokens off screen. Use the existing product recording for a quick preview. [Local walkthrough](demo/queuesense-walkthrough.webm) · [Setup](DEPLOYMENT_GUIDE.md#run-the-full-synthetic-demo)

| Time | Show | Narration |
| --- | --- | --- |
| 0:00–0:25 | Welcome, then live queue | “QueueSense addresses a common clinic problem. Patients want to know when they’ll be called. Receptionists and clinicians need to agree on who’s next. Managers need enough history to see where delays accumulate. QueueSense gives them a shared source of truth while keeping a patient’s view limited to one visit.” |
| 0:25–1:05 | Issue a token, then follow it in a second window | “Reception checks in a synthetic visit. FastAPI checks the staff session and role, then allocates the next token in a PostgreSQL transaction. The patient sees a private tracker. When an authorized clinician calls, starts and completes the visit, the screens refresh from change events sent after commit. The manager can then see the measured wait and compare it with the estimate recorded at check-in.” |
| 1:05–1:37 | Architecture and permissions | “Next.js handles the browser experience and forwards approved requests to private FastAPI routes. FastAPI issues a short-lived staff JWT and keeps a hashed refresh credential in PostgreSQL. On protected requests it verifies the JWT and checks the current session and permissions. Logout revokes the session. The backend also checks which clinician is assigned to a visit before allowing an update.” |
| 1:37–2:20 | Partner request-flow diagram and OpenAPI | “The Choreo integration is designed around one read-only operation, a weekly waiting-time summary. A subscribed application would present its OAuth token at the gateway. The dedicated HTTPS origin expects mutual TLS and a separate signed gateway assertion. It verifies that assertion, checks the department grant, and suppresses small cohorts. The HTTPS origin and assertion checks passed with synthetic credentials in local staging. Hosted Choreo verification still needs organization access.” |
| 2:20–2:51 | Developer Portal guide and Postman collection | “After the approved API is published, an application developer creates an application in the Developer Portal, adds a subscription and selects an approved plan. They generate credentials for that environment, obtain an OAuth token using client credentials, and invoke the versioned endpoint. The OpenAPI contract and Postman collection are ready for that workflow. This is the documented flow for a future hosted verification.” |
| 2:51–3:22 | 429 evidence and monitoring table | “FastAPI shares its rate-limit counters across workers through PostgreSQL. The partner origin allows thirty requests a minute per configured department. When that budget is exhausted, it returns 429 and a Retry-After value. In staging, that response survived HTTPS forwarding. Private metrics report errors and latency, while the request ID links the browser response to safe server logs. Choreo Insights will show gateway traffic once the proxy is deployed.” |
| 3:22–4:15 | Performance comparison, then deployment evidence | “The hardest problems were avoiding duplicate tokens under concurrent check-ins, keeping doctor actions scoped to assigned visits, and choosing a partner API small enough to review. Connection pooling and narrower queries lowered overall p95 from sixty to forty-four milliseconds at a hundred simulated users. Token issuance had a worse p99, which needs a longer staging run. The repository includes the load harness, CI workflows, and a Docker smoke test that stops and restarts PostgreSQL and FastAPI. The next milestone is executing the hosted Development and subscriber checklist.” |
