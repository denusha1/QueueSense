# QueueSense and Choreo authentication

## Trust boundaries

| Hop | Credential and enforcement |
| --- | --- |
| Clinic browser to QueueSense | Existing staff session cookies and QueueSense-issued HS256 JWTs. FastAPI verifies its issuer, audience and session, then looks up staff permissions in PostgreSQL. Patient capability links keep their existing access model. |
| Approved client to Choreo | OAuth 2.0 bearer token from the approved key manager. For non-interactive clients, use client credentials issued to a subscribed Developer Portal application. Choreo validates the credential and enforces the enabled operation and quota policies. |
| Choreo to integration ingress | TLS with gateway client certificate verification. Apply a strict method and path allowlist at the ingress. |
| Gateway to Future QueueSense integration route | Verify Choreo's signed `X-JWT-Assertion` against a configured gateway JWKS and dedicated audience. Resolve local client and clinic grants before running any aggregate query. |

Only the first row is implemented in QueueSense today. The [checked-in preview](openapi.yaml) declares staff bearer authentication, so a successful Choreo client-credentials token alone cannot invoke the current analytics route. The proxy should keep OAuth enabled. Finish the partner-specific verifier, grant checks and data filtering before using the pilot with partner credentials. Keep QueueSense's staff signing secret and refresh cookies within the existing QueueSense trust boundary. [QueueSense JWT configuration](../docs/JWT_AUTHENTICATION.md) · [Official OAuth consumption guide](https://choreolabs.com/engineering-platform/developer-platform/docs/tutorials/consume-an-api-hosted-in-choreo/)

## Console and origin steps after approval

1. In the API Proxy component, open **Deploy → Build Area → Security Settings**. Verify OAuth2 and security for the single resource. Enable **Pass Security Context To Backend** and enter the approved environment-specific value in **End User Token Audiences**. Apply the changes and redeploy. Set the audience explicitly because the forwarded assertion omits `aud` by default. Use the documented regional backend-assertion JWKS for the gateway serving the environment. The official guide lists US East and EU North addresses and gives `https://<PDP_GATEWAY_DOMAIN>/.wellknown/jwks` for private data planes. Verify the address against the approved data plane before trusting it. [Official security context and JWKS guide](https://wso2.com/engineering-platform/developer-platform/docs/developer/authentication-and-authorization/pass-end-user-attributes-to-upstream-services/)
2. For gateway-to-origin mTLS, open **Develop → Endpoints → Configure** for the selected API Proxy endpoint. Select or upload the origin server certificate if required. Turn on **Mutual SSL** and choose **Add Client Certificate → Generate new key pair** when platform-generated certificates are approved. Download the public certificate through **View and Download**, have the ingress owner trust it, select the pair under **Existing Certificates**, and save. Deploy using the correct environment endpoint and certificate pair. [Official mTLS setup and promotion steps](https://wso2.com/engineering-platform/developer-platform/docs/authentication-and-authorization/secure-communication-between-the-choreo-gateway-and-your-backend-with-mutual-tls/)
3. Implement a separate integration dependency. Check the single assertion header, signature, configured issuer and audience, expiry and time bounds. Fix the allowed signing algorithm to the verified deployment configuration and resolve `kid` only from the trusted JWKS. Map the observed machine-client application identifier and context to an approved local grant with explicit department access. Claims shown in documentation examples may be optional or vary by token grant. Fail closed until the machine-client claim profile is verified. [Official assertion claims reference](https://wso2.com/engineering-platform/developer-platform/docs/developer/authentication-and-authorization/pass-end-user-attributes-to-upstream-services/)
4. Verify a valid subscribed invocation and negative cases for missing, expired or wrong-audience assertions, duplicate assertion headers, incorrect application or department, absent gateway certificate and access outside the route allowlist. Keep minimized logs with request IDs and categorical failures. Capture the status and rate-limit headers at the gateway separately from QueueSense-origin errors.

## Credentials and approvals

The owner approves repository access, the hosting account and data plane, environment secret creation, the selected key manager, and any egress rules or certificate changes. The owner also approves any Developer Portal application, subscription plan, audience visibility and production promotion. Transfer customer-managed credentials through the approved secret store. Use independent keys and certificates for Development and Production, and rehearse rotation and emergency revocation before partner traffic. [Integration runbook](choreo-integration-plan.md)
