# QueueSense Choreo integration plan

Reviewed against official WSO2 Developer Platform documentation on 26 November 2026. This plan uses the managed console at `console.choreo.dev`. It prepares an origin image and a contract for private review. Hosted deployment, proxy activation, publication and subscriptions require the owner’s console access and approval. [Official platform documentation](https://wso2.com/engineering-platform/developer-platform/docs/) · [Managed console](https://console.choreo.dev/)

## Repository work completed

- The [backend Dockerfile](../backend/Dockerfile) installs the locked Python dependencies, copies the application and model, and starts `backend.app:create_app` on `0.0.0.0:8001`. It now declares numeric UID `10001`, in the range required by the Docker workflow. Uvicorn disables direct access logs and proxy-header trust. [Official Docker service workflow](https://wso2.com/engineering-platform/developer-platform/docs/develop-components/develop-services/develop-a-service-with-docker/)
- The [OpenAPI 3.0.3 file](openapi.yaml) is generated from the current FastAPI contract and contains one GET operation. It deliberately has a relative origin path and no guessed gateway host. It describes the existing staff JWT, parameter constraints and origin errors. The production application hides its complete generated schema. [Exposure rules](api-exposure.md) · [Authentication plan](security-integration.md)
- PostgreSQL migrations and runtime grants stay separate from the API process. The readiness endpoint exercises database access for the runtime role. Apply migrations through `017_staff_authorization.sql` using the release/owner credential before first startup. [Migration runner](../database/scripts/manage.py) · [Runtime grants](../database/sql/product_runtime_grants.sql)

To regenerate or check contract drift, use the backend's locked virtual environment with PyYAML available. PyYAML and `openapi-spec-validator` are tooling only. Install them in a verification environment alongside the backend lock. Run from the repository root.

```sh
PYTHONPATH=. python api-management/generate_openapi.py
PYTHONPATH=. python api-management/generate_openapi.py --check
python -m openapi_spec_validator api-management/openapi.yaml
docker build -f backend/Dockerfile -t queuesense-api:local .
```

## Owner console steps for the private Service

1. Sign in to the managed console and select the authorized organization and project. Open **+ Create → Service**. In the source fields, select the authorized repository and branch that contain `backend/` and `ml/` at their root. Set **Component Directory** to `/` and choose the **Docker** build preset. Set **Dockerfile** to `/backend/Dockerfile`. Use the repository rooted at the QueueSense application. The outer workspace checkout contains the application as a Git submodule. [Official Docker component creation](https://wso2.com/engineering-platform/developer-platform/docs/develop-components/develop-services/develop-a-service-with-docker/)
2. Configure the HTTP REST endpoint on port `8001` with **Project** network visibility. Leave the service context at root so the runtime receives its existing route paths. This is a private backend endpoint. In a Docker build without a repository endpoint manifest, use the basic endpoint configuration in the Console. Review endpoint details before deploying. [Official endpoint configuration](https://com-migration.wso2.com/choreo/docs/develop-components/configure-endpoints/)
3. For Development, provision privately reachable PostgreSQL, create the least-privilege runtime role `queuesense_auth`, and apply the migrations and both grant scripts as an authorized owner. In the Service component, select **Build → Build Latest**. Wait for **Success** and review the Dockerfile and container scan results. [Official Docker deployment workflow](https://wso2.com/engineering-platform/developer-platform/docs/develop-components/develop-services/develop-a-service-with-docker/)
4. Select **Deploy → Set Up → Configure & Deploy**. Populate the environment configuration before deploying. Enter `DATABASE_URL` for the runtime user and `JWT_SIGNING_SECRET` as secrets. Set `APP_ENV=production`, `ENABLE_DEMO_LOGIN=false`, and `FRONTEND_ORIGINS` to the exact allowed HTTPS browser origin or origins. Use a PostgreSQL connection with certificate verification as supported by the chosen host. For the isolated smoke environment set `ENABLE_AUTOMATION=false` so it sends no background messages. Use a separately approved configuration for real automation. For configuration changes after deployment, use **Deploy → Development → Manage Configs and Secrets → Environment Variables → + Add a Configuration**. [Official configuration and secrets workflow](https://wso2.com/engineering-platform/developer-platform/docs/devops-and-ci-cd/manage-configurations-and-secrets/)
5. Review **Endpoint Details**, deploy, and wait for **Development → Active**. In **DevOps → Health Checks**, create a TCP liveness probe on `8001` and an HTTP readiness probe for `GET /health` on `8001`. Confirm the running instance under **DevOps → Runtime**. Record the environment's actual private service address from the deployment's endpoint details. From an authorized workload in the project, call `GET /health` and record HTTP 200 with `{"status":"ok"}`. [Official health check setup](https://wso2.com/engineering-platform/developer-platform/docs/devops-and-ci-cd/set-up-health-checks/)

## Owner console steps for the API Proxy

The checked-in contract can be reviewed in the import form with a confirmed synthetic origin. Keep it in **Created** during this stage. A managed partner invocation requires the separate integration endpoint, gateway-assertion verification, and department and cohort controls in the [security plan](security-integration.md). Deploy the proxy for traffic only after those controls and its revised contract are available.

1. In the project choose **+ Create → API Proxy → Upload API Specification**. Upload `api-management/openapi.yaml` for private import review. Then set the metadata. Preview display name can be `QueueSense Waiting Time Private Preview`, unique component name `queuesense-wait-time-preview`, context `queuesense-wait-time-preview`, and API version `v1.0`. Set **Target** to the verified synthetic ingress URL with the `/api/v1/analytics` suffix. For the future partner component, upload its revised contract and use its approved integration ingress and base path. Confirm **Develop → Resources** lists exactly the intended GET operation. [Official contract upload workflow](https://wso2.com/engineering-platform/developer-platform/docs/develop-components/develop-proxy/develop-an-api-proxy-from-an-open-api-specification/)
2. After origin security and approval, use **Deploy → Build Area → Security Settings** to keep OAuth2 enabled and enable the signed backend assertion. Configure the endpoint certificate and mTLS. Use **Deploy → Build Area → Configure & Deploy** for Development. Select the access mode required by the approved audience. **External** exposes a public gateway endpoint and requires approval. Review the actual Target during deploy. [Official deployment workflow](https://wso2.com/engineering-platform/developer-platform/docs/tutorials/expose-a-service-as-a-managed-api/) · [Security runbook](security-integration.md)
3. In **Test → OpenAPI Console**, select Development, choose the GET resource and run a synthetic request. Separately test with a machine-client token through the gateway before promoting. Verify the exact origin path, authorization and excluded routes. Configure tested API limits on the environment's **CORS, Rate Limiting and Resiliency** panel. Document the gateway's actual rejection responses separately from FastAPI's envelope. [Official testing and rate limiting workflow](https://wso2.com/engineering-platform/developer-platform/docs/develop-components/develop-proxy/develop-an-api-proxy-from-an-open-api-specification/)

## API lifecycle and approval

- **Created** during preparation. Use **Manage → Lifecycle → Pre-release** only if the owner approves a portal-visible pilot. Confirm portal exposure by environment in the organization's Developer Portal settings.
- **Published** after the owner accepts the verified integration. Use **Deploy → Development → Promote**, verify Production is **Active** and retest using Production's separate endpoint and certificates. Select **Manage → API Info → Developer Portal** and set the approved Visibility before publishing. Use **Restricted** with named roles for the initial approved audience where available. Use **Manage → Lifecycle → Publish → Confirm**, then verify the listing and invocation URL in the Developer Portal. Visibility controls discoverability. Gateway credentials, subscription policy, and origin grants control invocation.
- **Subscription and credentials** require the owner’s approval. In the Developer Portal, use **Applications → + Create** to name and create an approved application, or select its existing entry under **Applications**. Open **Subscriptions → + Add APIs** and select the approved API and plan. Use that application's **Credentials** for the intended environment to generate authorized OAuth credentials. Read the actual token endpoint from the portal and use the client credentials grant. Portal test tokens are limited to testing. [Official subscription and client credentials workflow](https://choreolabs.com/engineering-platform/developer-platform/docs/tutorials/consume-an-api-hosted-in-choreo/)
- **Versioning and retirement.** Use compatible changes within a major version and a new major version for breaking changes. A newly published minor version becomes the default invocation for its major, so verify the major URL on release. Capture the previous image revision, proxy configuration and contract before promoting. Use **Manage → Lifecycle** with publishing privilege to move a superseded version to **Deprecated** after notifying consumers. Deprecation is irreversible. Use **Retired** after consumers migrate and the owner accepts retirement. [Official lifecycle rules](https://wso2.com/engineering-platform/developer-platform/docs/api-management/lifecycle-management/) · [Official portal visibility workflow](https://wso2.com/engineering-platform/developer-platform/docs/api-management/control-api-visibility/)

## Local verification

- The contract passed OpenAPI 3.0 validation and the generator's drift check. Both the measured and empty waiting-time response examples passed schema validation.
- All 138 backend tests passed against local PostgreSQL. A production-mode Uvicorn smoke test with the restricted database role confirmed readiness returns `200` and `{"status":"ok"}` with the database available and a sanitized `503` when the database is unavailable. It also confirmed the origin rejects unauthenticated analytics requests and hides the live OpenAPI endpoint.

- The Linux ARM64 Docker image built from the repository root. The isolated container smoke test confirmed UID 10001, port 8001, readiness HTTP 200 with PostgreSQL and 503 after PostgreSQL stopped. It also confirmed the analytics operation returned 401 without credentials and 200 with a synthetic Manager staff JWT. The full OpenAPI endpoint returned 404 in production mode.

## Evidence to record

Record the image revision, environment, internal Service address, readiness checks, validated contract revision, exact proxy Target and invocation URL, asserted machine-client claim profile, subscription and applicable approval. Capture synthetic evidence for accepted and denied requests, origin bypass prevention, rate limits and rollback. Keep credentials, cookies, patient links and full assertions out of the evidence. The integration route, ingress, hosted Service and gateway remain rollout work. The root origin and partner invocation hostname will come from the actual approved environment.
